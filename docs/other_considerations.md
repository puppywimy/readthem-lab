# Other Considerations

이미 논의를 거쳐 결정된 내용을 다시 논의하지 않도록 기록하는 문서입니다. 왜 그 방식을 선택했는지 바로 알기 어려운 결정만 적고, 코드나 다른 문서에서 알 수 있는 구현 상세는 적지 않습니다.

## DB 스키마는 Flyway로 관리한다

스키마는 `back/src/main/resources/db/migration/`의 마이그레이션 파일이 기준이고, JPA는 `ddl-auto: validate`로 엔티티와 스키마가 맞는지만 확인합니다.

- 스키마 변경이 기록으로 남고, 적용 전에 리뷰할 수 있으며, 배포 시 자동으로 적용됩니다.
- 도서 검색용 FULLTEXT 인덱스처럼 엔티티로 표현할 수 없는 스키마를 저장소에서 관리할 수 있습니다.
- 대신 엔티티를 바꿀 때마다 마이그레이션 파일을 함께 써야 합니다. 스키마를 한 곳에서 명시적으로 관리하는 이점이 더 크다고 판단했습니다.

## 로컬·테스트 DB도 MySQL을 쓴다 (H2 제거)

마이그레이션에 H2에서 실행되지 않는 MySQL 문법(FULLTEXT 인덱스 등)이 들어가므로 H2를 걷어냈습니다. 로컬은 `infra/local/compose.yaml`의 MySQL, 테스트는 Testcontainers의 MySQL을 씁니다. 그래서 테스트 실행에는 Docker가 필요합니다.

## 인증 쿠키 SameSite

- `cookieSecure=true`(운영)면 `SameSite=None`, 아니면 `Strict`를 쓴다. (`Rq.setCookie`)
- 이유: 프론트(`pages.dev`)와 백엔드가 서로 다른 사이트라 운영에서는 `None`이 필요하고, `None`은 `Secure` 없이는 브라우저가 거부해 로컬에서는 `Strict`를 쓴다.
- `CUSTOM__PROD__COOKIE_DOMAIN`은 프론트가 아니라 백엔드 도메인이어야 한다.
- 한계: 서드파티 쿠키를 차단하는 브라우저(Safari, Chrome 시크릿)에서는 로그인이 유지되지 않는다. 프론트와 백엔드를 같은 사이트로 묶으면 운영도 `Strict`로 되돌릴 수 있다.

## 도서 검색은 제목·저자 전처리 컬럼에서 구문 검색하는 방식으로 구현했습니다.

- 기호 7개를 대체 문자로 바꿨습니다. ngram 파서는 기호를 구분자로 취급하므로, 글자로 분류되면서 일반 텍스트에 거의 나오지 않는 유니코드 글자로 바꿉니다.
- 지금 필요한 제목·저자 구문 검색을 전처리 방식으로 구현 가능하며, 새로운 기술을 도입하는 것보다 저렴하다고 판단하여 Elasticsearch를 도입하지 않았습니다. 추후 오타 허용, 형태소 단위 검색, 여러 조건을 섞은 정렬이 필요해지거나 검색 부하가 DB에 부담이 되면 검토합니다. FULLTEXT 쿼리의 메모리 문제로 다시 검토한 내용은 아래 '도서 검색의 FULLTEXT 쿼리는 메모리 상한과 동시 실행 수로 묶는다'에 있습니다. 지금 방식은 Elasticsearch 분석기(문자 필터 → 토크나이저)가 하는 일을 생성 컬럼과 Kotlin에 구현한 것이라 규칙을 그대로 옮길 수 있습니다.

- 정렬은 제목 완전 일치 → 제목 앞부분 일치 → 저자 앞부분 일치 → 나머지(관련도 순)이고, 단계마다 인덱스로 필요한 만큼만 조회해 이어 붙입니다(#73). 한 쿼리로 정렬하면 매칭된 행 전부에 접근해야 해서 흔한 검색어가 수 초씩 걸렸습니다. 관련도만으로 정렬하면 빠르지만 검색어를 여러 번 반복한 제목이 맨 위에 옵니다.
- 2·3단계(제목·저자 앞부분 일치)는 옵티마이저의 선택과 상관없이 `search_title`, `search_author` 인덱스를 강제합니다. 옵티마이저는 `ORDER BY id DESC LIMIT`을 보고 PK 역순 스캔을 고를 때가 있고, 맞는 행이 오래된 id에 몰린 검색어에서는 수십만 행을 읽어 1초 넘게 걸렸습니다. 맞는 행이 최근 id에 몰린 검색어는 PK 역순이 더 빠를 수 있지만 아끼는 시간은 수십 ms이고 최악은 초 단위라, 응답 시간 상한이 정해지는 쪽을 택했습니다. 사용자의 검색 패턴(자주 쓰는 검색어, 넘기는 페이지 수)을 분석해 최적화가 필요해지면 다시 검토합니다.
- 1\~3단계에 쓰는 `search_title`, `search_author`는 B-Tree 인덱스 키 길이 제한 때문에 255자로 자릅니다. 255자를 넘는 제목·저자는 잘린 값으로 비교되지만 그런 도서는 드물고, 프론트에서 검색어를 100자로 제한하고 있어 그대로 둡니다.
- 저자는 완전 일치가 아니라 앞부분 일치로 봅니다. `authors`에 `최영근 역`처럼 역할이 붙어 있어 전처리하면 `최영근역`이 되기 때문입니다. 저자가 여러 명이면 첫 번째 저자만 앞부분 일치로 잡힙니다.
- 한 글자 검색은 1\~3단계(제목 완전 일치, 제목·저자 앞부분 일치)에서만 결과가 나옵니다. FULLTEXT 인덱스가 두 글자 단위(`ngram_token_size=2`)라 한 글자 구문 검색은 아무 행도 찾지 못해 4단계가 비기 때문입니다. 그래서 '다시, 봄'처럼 한 글자가 제목 중간에 있는 도서는 '봄'으로 검색해도 나오지 않습니다. 한 글자를 어디든 포함하는 도서는 '이', '개'처럼 흔한 글자면 수십만 건이라 결과로서 쓸모가 없고, 찾으려면 `LIKE '%봄%'`로 전체 행을 읽어야 해 초 단위가 걸리므로 앞부분 일치로 충분하다고 판단했습니다.

## 도서 검색은 오프셋 페이지네이션을 쓴다

도서 검색의 페이지 처리는 커서가 아니라 오프셋(`page`, `size`) 방식입니다.

- 커서 방식은 쓸 수 없는 구조입니다. 4단계(나머지)는 FULLTEXT 관련도 순인데, FULLTEXT 인덱스는 "관련도가 X보다 작은 곳부터" 찾아가지 못합니다. 그런 조건을 걸면 정렬된 순서로 읽는 빠른 경로가 깨져 매칭된 행 전부를 읽게 됩니다.
- 오프셋 방식은 뒤 페이지로 갈수록 단계마다 `offset + size`건씩 읽어야 해서 무거워집니다. 이 부담은 지연 조인으로 줄입니다. 단계별 조회는 인덱스에서 `id`만 고르고, 도서 행 전체는 최종 `size`건만 조인해 읽습니다.
- 페이지를 넘기는 도중 도서가 추가되면 결과가 밀려 중복·누락이 생길 수 있지만, 지금은 그런 경우가 드물다고 판단했습니다. 도서 수집이 자동으로 돌지 않고, 관리자의 도서 수정·삭제도 드뭅니다.

## 도서 검색의 FULLTEXT 쿼리는 메모리 상한과 동시 실행 수로 묶는다

4단계(FULLTEXT 구문 검색)는 검색어에 따라 쿼리 하나가 1GB 넘게 메모리를 써서 운영 DB가 swap으로 느려지거나 종료됐습니다(#66). 메모리는 검색어 토큰들의 문서 목록 길이 합에 비례하고, 같은 토큰이 반복되면 그만큼 더 늘어납니다. 그래서 쿼리 하나의 메모리에 상한을 두고, 동시에 도는 FULLTEXT 검색 수를 제한합니다. 상한에 걸려 쿼리가 실패하거나 자리가 나지 않으면 1\~3단계(제목 완전 일치, 제목·저자 앞부분 일치) 결과로 응답합니다. 애플리케이션 쪽 제한은 `BookService.getBooksBySearch`, MySQL 설정은 #82에서 다룹니다.

- 정확도 손실: 폴백하면 4단계가 빠져 제목·저자 중간에 검색어가 든 도서가 나오지 않습니다. 응답은 여전히 200이고 폴백했다는 표시는 없습니다. 폴백은 로그(`FULLTEXT search skipped`, `FULLTEXT search failed`)로만 확인합니다. 로그에는 개인정보가 될 수 있는 검색어 원문 대신 전처리한 검색어의 길이와 ngram 토큰 수만 남깁니다.
- FULLTEXT 실패 시 예전에는 `title LIKE '%…%'`로 넘어갔지만 565만 행을 모두 읽어 DB를 더 괴롭히므로 지웠습니다.
- 메모리 상한 512MB(`innodb_ft_result_cache_limit`, 기본값은 약 2GB라 사실상 제한이 없음): 운영 덤프(565만 건)로 잰 결과 한글 검색어와 실제 도서 제목은 대부분 256MB 안이었고, 영문 일반 단어는 `spring` 약 358MB, `programming` 약 567MB, 반복 토큰(`ninninninninninnin`)은 약 1GB였습니다. 512MB는 흔한 검색어는 그대로 통과시키고 1GB급 쿼리는 막는 값입니다. `programming`처럼 상한을 넘는 영문 일반 단어는 폴백합니다.
- 동시 실행 수 2, 대기 1초(`custom.book-search.full-text.max-concurrent`, `acquire-timeout`): 상한이 쿼리 하나만 묶으므로, 동시 실행 수를 함께 제한해야 FULLTEXT 검색 전체가 쓰는 메모리가 `512MB × 2` 안으로 묶입니다. 1\~3단계는 B-Tree 인덱스만 써서 제한하지 않습니다. 제한은 애플리케이션 인스턴스마다 걸리므로 Blue/Green 전환 중 두 인스턴스가 함께 뜨는 동안에는 최대 4개까지 돌 수 있습니다.
- 영문 검색어를 단어 단위로 검색하는 분기는 지금 하지 않습니다. 지금 방식은 언어와 상관없이 모든 검색어의 메모리를 묶어 DB가 죽는 것을 막고, 단어 단위 검색은 영문에만 효과가 있으면서 별도 FULLTEXT 인덱스(파서가 다른)의 저장 공간·쓰기 비용이 들고, 2글자 이하 영문 단어(`C`, `Go`, `AI` 등)를 따로 처리해야 합니다.
- 폴백이 많아지면 먼저 흔한 토큰(문서 목록이 긴 ngram 토큰)을 FULLTEXT 조건에서 빼는 방법을 시도합니다. 구문 일치 확인은 이미 있는 `search_text LIKE` 조건이 하므로, 드문 토큰만으로 후보를 좁혀도 찾는 도서는 같고 메모리는 줄어듭니다. 다만 4단계의 관련도 점수가 달라지므로 정렬이 바뀌는지 함께 확인합니다.
- Elasticsearch는 이번에도 도입하지 않습니다. 쿼리 메모리 문제는 구조상 해결되지만(문서 목록을 메모리에 모으지 않고 상위 결과만 유지), 상시로 띄워 둘 메모리가 더 필요해 지금 서버 규모에는 부담이 큽니다. 위 방법을 적용해도 폴백이 계속 많으면 다시 검토합니다.

## 영어 원서는 지금 다루지 않는다

도서 데이터는 국립중앙도서관 ISBN·CIP 서지정보 API(`nl.go.kr/seoji`)에서 받습니다. 이 API에는 국내 출판사가 ISBN을 발급받을 때 등록한 자료만 있어서, 해외에서 출판된 원서는 처음부터 들어 있지 않습니다. 번역서는 들어 있습니다.

- 개발 서적은 원서로 읽는 수요가 있지만, 지금 있는 국내 도서(약 565만 건)도 아직 정제되지 않았습니다. 원서까지 넣으면 정제하고 검색해야 할 노이즈가 늘어나므로 국내 도서 검색을 먼저 완성합니다.
- 원서를 한꺼번에 받아올 출처도 마땅치 않습니다. Google Books나 Open Library는 개발서만 골라 받기 어렵고 품질도 제각각입니다.
- 나중에 원서를 다룬다면 대량으로 받지 않습니다. 사용자가 원서를 찾았는데 결과가 없을 때 ISBN으로 외부 API를 조회해 그 한 건만 추가하는 방식을 검토합니다. 원서와 번역서는 종이책·전자책·권차와 같은 방식으로 "같은 작품"으로 묶습니다.

## 도서 표지는 카카오 썸네일로 통일한다

국립중앙도서관 API의 표지 주소(`TITLE_URL`)에는 원본 해상도가 지나치게 큰 이미지(예: 6872×9746)가 섞여 있어, 홈 표지 벽에 하나만 섞여도 첫 접속·탭 전환·hover 때 벽이 끊겼습니다(#60). 그래서 표지 주소를 모두 비우고(V4 마이그레이션) 도서 수집 때도 저장하지 않으며, 도서가 조회될 때 카카오 썸네일 주소로 채웁니다.

- 관리자 도서 수정 폼의 표지 주소 입력은 비활성화했습니다. 관리자가 원본 크기의 이미지를 넣으면 같은 문제가 다시 생기기 때문입니다.
- 카카오 호출에 실패하면 "표지 없음"으로 기록하지 않습니다. 기록하면 일시적인 실패로도 그 도서는 다시 조회하지 않게 됩니다.
- 카카오 썸네일은 작은 크기라 큰 표지가 필요한 곳에서는 흐리게 보일 수 있습니다. 표지를 직접 리사이즈해 관리하는 방식은 우선순위가 낮아 이번에는 하지 않았습니다. 나중에 한다면 수집 단계에서 리사이즈해 Object Storage에 올리는 방식을 검토합니다.

## Next.js는 16.3.0 이상을 쓴다

16.2.x에서는 정적 빌드에서 도서 검색어가 첫 검색어로 고정됩니다. 16.3.0에서 고쳐졌습니다([vercel/next.js#94144](https://github.com/vercel/next.js/pull/94144)).

**라우터 캐시**

- 키는 `(경로, 쿼리 파라미터)`이고, 값에는 페이지 구조(`tree`)와 이동 후 주소창에 설정할 주소(`canonicalUrl`)가 들어갑니다.
- 이동할 때는 먼저 이동할 주소의 키를 그대로 찾습니다. 없으면 쿼리 파라미터를 비운 키를 찾아, 그 tree를 복사하고 주소만 바꿔 이동합니다. 복사본은 캐시에 저장하지 않습니다.
- 이때 비운 키의 `canonicalUrl`에 쿼리 파라미터가 붙어 있으면 리다이렉트로 보고 그 쿼리 파라미터로 이동합니다.
- 헤더의 "도서 검색" 링크는 모든 페이지에 있어서, 페이지가 로드되면 prefetch가 `("/books/search", "")` 키를 채웁니다. 정적 빌드도 빌드할 때 prefetch용 RSC 파일을 만들어 두므로 prefetch가 동작합니다. `pnpm dev`에서는 prefetch가 꺼져 있습니다.

**16.2.x의 문제**

16.2.x는 키의 쿼리 파라미터 자리에 실제 주소의 쿼리 파라미터가 아니라 페이지를 렌더링할 때 쓴 쿼리 파라미터(RSC 페이로드의 `q`)를 넣습니다. 정적 빌드는 빌드할 때 쿼리 값을 알 수 없어 경로마다 파일을 하나씩만 만듭니다. 그래서 검색 페이지도 검색어 없이 빌드되고, `q`는 항상 빈 값입니다.

1. `/books/search?searchTerm=AAA`로 직접 접속하면 `("/books/search", "")` 키에 `canonicalUrl: /books/search?searchTerm=AAA`가 저장됩니다.
2. 이후 다른 검색어로 이동하면 그 검색어의 키가 없으므로 `("/books/search", "")` 키를 찾습니다.
3. `canonicalUrl`에 `?searchTerm=AAA`가 붙어 있으니 리다이렉트로 보고 AAA로 이동합니다. 헤더의 "도서 검색"을 눌러도 같은 키를 찾으므로 AAA로 이동합니다.

**16.3.0부터의 흐름**

키에 실제 주소의 쿼리 파라미터를 넣습니다. 바뀐 건 이것뿐이고, 이동할 때 키를 찾는 순서와 복사하는 방식은 같습니다.

- 홈 등에서 들어와 검색하면 prefetch가 채운 `("/books/search", "")`의 tree를 복사해 이동합니다. 검색을 몇 번 해도 새 키가 생기지 않고 요청은 0건입니다.
- `/books/search`로 직접 접속하면 그 접속이 `("/books/search", "")` 키를 만들고, 이후 검색은 위와 같습니다.
- `?searchTerm=AAA`로 직접 접속하면 `("/books/search", "?searchTerm=AAA")` 키가 따로 생기고 `("/books/search", "")` 키는 오염되지 않습니다. 이 키는 같은 검색어로 다시 가거나 뒤로 가기로 돌아올 때만 쓰입니다.
- prefetch가 끝나기 전이나 만료된 뒤라 `("/books/search", "")` 키가 비어 있으면, RSC 파일 1건을 받아 그 검색어의 키에 저장합니다. 이 경우에도 페이지 전체를 다시 받지는 않습니다.

**확인 방법**

`pnpm dev`에서는 요청마다 렌더링해 `q`가 실제 쿼리 파라미터와 같으므로 문제가 드러나지 않습니다. Next 버전을 바꿀 때는 정적 빌드에서 `?searchTerm=AAA`로 직접 들어온 뒤 다른 검색어로 검색하고 헤더의 "도서 검색"을 눌러 확인합니다. 헤더 링크의 prefetch가 있는 경우와 없는 경우를 모두 확인합니다.

## Pretendard는 원본 가변 폰트 파일 하나를 직접 호스팅한다

jsDelivr의 다이나믹 서브셋 CSS 대신 `next/font/local`로 `PretendardVariable.woff2`(약 2MB)를 직접 호스팅합니다.

- 다이나믹 서브셋은 외부 CSS를 받은 뒤에야 woff2 조각을 요청하고, 조각이 도착할 때마다 해당 글자만 교체되어 레이아웃이 여러 번 움직였습니다. 파일 하나를 preload하면 빠른 네트워크에서는 첫 렌더 전에 폰트가 도착해 교체가 없고, 느린 네트워크에서도 교체가 한 번으로 줄어듭니다.
- 대신 첫 방문 전송량이 늘어납니다(홈 기준 약 280KB → 2MB). 느린 네트워크에서는 폰트가 늦게 도착해 시스템 폰트로 보이는 시간이 길어집니다. 이후 방문은 캐시를 씁니다.
- `next/font`가 만드는 크기 보정 대체 폰트는 Arial 기반이라 한글에는 적용되지 않습니다. 한글은 교체 전까지 보정 없는 시스템 폰트로 보입니다.
- Pretendard 글리프 목록(`subset_glyphs.txt`, 한글 2,780자)으로 서브셋을 만들면 약 630KB가 되지만 쓰지 않았습니다. 목록 밖의 글자(드문 한글 음절 등)가 시스템 폰트로 보이고, SIL OFL의 예약 글꼴명(Pretendard) 조항상 수정본을 같은 이름으로 배포할 수 있는지 확인이 필요합니다. 첫 방문 전송량이 문제가 되면 다시 검토합니다.
