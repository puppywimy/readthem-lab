# Other Considerations

이미 논의를 거쳐 결정된 내용을 다시 논의하지 않도록 기록하는 문서입니다.

## DB 스키마는 Flyway로 관리한다

스키마는 `back/src/main/resources/db/migration/`의 마이그레이션 파일이 기준이고, JPA는 `ddl-auto: validate`로 엔티티와 스키마가 맞는지만 확인합니다.

- 스키마 변경이 기록으로 남고, 적용 전에 리뷰할 수 있으며, 배포 시 자동으로 적용됩니다.
- 도서 검색용 FULLTEXT 인덱스처럼 엔티티로 표현할 수 없는 스키마를 저장소에서 관리할 수 있습니다.
- 대신 엔티티를 바꿀 때마다 마이그레이션 파일을 함께 써야 합니다. 스키마를 한 곳에서 명시적으로 관리하는 이점이 더 크다고 판단했습니다.

## 로컬·테스트 DB도 MySQL을 쓴다 (H2 제거)

마이그레이션에 H2에서 실행되지 않는 MySQL 문법(FULLTEXT 인덱스 등)이 들어가므로 H2를 걷어냈습니다. 로컬은 `infra/local/compose.yaml`의 MySQL, 테스트는 Testcontainers의 MySQL을 씁니다. 그래서 테스트 실행에는 Docker가 필요합니다.

## 인증 쿠키 SameSite

- `cookieSecure=true`(운영)면 `SameSite=None`, 아니면 `Strict`를 쓴다. (`Rq.setCookie`)
- 이유: 프론트(`pages.dev`)와 백엔드가 서로 다른 사이트라 운영에서는 `None`이 필요하고, `None`은 `Secure` 없이는 브라우저가 거부해 로컬에서는 `Strict`를 쓴다.
- `CUSTOM__PROD__COOKIE_DOMAIN`은 프론트가 아니라 백엔드 도메인이어야 한다.
- 한계: 서드파티 쿠키를 차단하는 브라우저(Safari, Chrome 시크릿)에서는 로그인이 유지되지 않는다. 프론트와 백엔드를 같은 사이트로 묶으면 운영도 `Strict`로 되돌릴 수 있다.

## 도서 검색은 제목·저자 전처리 컬럼에서 구문 검색한다

검색어를 단어로 쪼개지 않고, 검색어 전체가 제목 또는 저자에 들어 있는 책을 찾습니다. (`BookRepository.searchByKeyword`)

- 제목과 저자에 같은 전처리를 적용한 STORED 생성 컬럼 `book.search_text`(`전처리한 제목 + 공백 + 전처리한 저자`)에 ngram FULLTEXT 인덱스를 두고, 전처리한 검색어를 따옴표로 감싸 `BOOLEAN MODE` 구문 검색합니다.
- 전처리 규칙: 기호 7개 `+ # & . : - /`를 대체 문자 `ǂ ǁ ǀ ǃ ƻ ʔ ƾ`로 바꾼 뒤, 글자(`\p{L}`)·숫자(`\p{Nd}`)가 아닌 문자(공백 포함)를 모두 지웁니다.
  - 공백은 무시합니다. `열혈 C`와 `열혈C`는 같은 검색입니다.
  - 기호 7개는 글자처럼 엄격하게 비교합니다. `C++`, `C#`, `M&A`, `Node.js`처럼 기호가 책을 구분하는 경우가 많아서입니다. 그래서 `Node.js`와 `nodejs`는 다른 검색입니다.
  - ngram 파서는 기호를 구분자로 취급하므로, 글자로 분류되면서 일반 텍스트에 거의 나오지 않는 유니코드 글자로 바꿉니다.
  - 대소문자는 컬럼 콜레이션(`utf8mb4_0900_ai_ci`)이 무시하므로 전처리에서 바꾸지 않습니다.
- 출판사는 검색 대상에서 뺐습니다.
- 규칙은 마이그레이션(SQL)과 `BookSearchTextNormalizer`(Kotlin) 두 곳에 있습니다. 어긋나면 검색 결과가 조용히 빠지므로 `BookSearchTextNormalizerRuleTest`가 두 결과를 비교합니다. 규칙을 바꾸면 새 마이그레이션으로 생성 컬럼을 다시 정의하고 Kotlin도 함께 고칩니다.
- 전처리 결과에는 글자·숫자·대체 문자만 남아 `BOOLEAN MODE` 연산자 문자가 문제를 일으키지 않습니다. 전처리 결과가 비면 쿼리를 보내지 않고 빈 결과를 돌려줍니다.
- 정렬은 제목 완전 일치 → 제목 앞부분 일치 → 관련도 내림차순 → `id` 내림차순입니다.
- 기존 인덱스 `ft_book_search` 제거는 배포를 나누지 않았습니다. Blue/Green 전환 중에는 이전 코드의 검색이 실패해 LIKE 검색으로 넘어가지만, 아직 사용자가 없어 감수했습니다.
- Elasticsearch는 도입하지 않았습니다. 지금 필요한 제목·저자 구문 검색이 MySQL로 되기 때문입니다. 오타 허용, 형태소 단위 검색, 여러 조건을 섞은 정렬이 필요해지거나 검색 부하가 DB에 부담이 되면 검토합니다. 지금 방식은 Elasticsearch 분석기(문자 필터 → 토크나이저)가 하는 일을 생성 컬럼과 Kotlin에 구현한 것이라 규칙을 그대로 옮길 수 있습니다.
